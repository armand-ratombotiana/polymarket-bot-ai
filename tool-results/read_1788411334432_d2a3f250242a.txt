    10→### Background / investigation
    11→- The trading pipeline already existed as discrete stages — ML predict →
    12→  signal generation → risk gate → order submission → fill — but each stage
    13→  logged to a different store (`audit_trail.db`, `store_state.json`,
    14→  in-memory `event_log`). Tracing the lifecycle of a single decision
    15→  required correlating timestamps across three data sources, with no
    16→  canonical id linking them.
    17→- `core/audit_logger.py` already establishes the SQLite + `asyncio.to_thread`
    18→  pattern used here; the new ledger mirrors that convention so the two
    19→  databases coexist without schema contention.
    20→- `strategies/signal_trader._ml_signal` is **synchronous** (returns
    21→  `MarketSignal | None` directly). The decision-ledger writes are async, so
    22→  the strategy uses a fire-and-forget pattern (`asyncio.ensure_future` on the
    23→  running loop) — this is critical because awaiting each ledger write inline
    24→  would block the 15 s scan cadence on SQLite I/O.
    25→- The four rejection paths in `_ml_signal` are:
    26→  1. `confidence < self._min_confidence` → `low_confidence`
    27→  2. `spread >= 0.04` → `wide_spread`
    28→  3. `0.45 < p_yes < 0.55` → `neutral_zone`
    29→  4. `kelly_numerator <= MIN_KELLY_NUMERATOR` → `insufficient_kelly_edge`
    30→  Each path now calls `record_rejection()` with `decision_id`, `predicted_edge`,
    31→  `confidence`, `reason`, and `market_mid` before returning `None`.
    32→- `OrderArgs` (in `core/clob_client.py`) is the canonical order-shape passed
    33→  to `paper_sim.create_order` and `clob_client.create_order`. The
    34→  `decision_id` is passed as a separate kwarg through `submit_order` →
    35→  `create_order` (NOT added to `OrderArgs` itself, keeping that dataclass
    36→  untouched per "additive only — do NOT remove existing code").

    38→### R11 — New `core/decision_ledger.py`
    39→
    40→#### Schema (SQLite, separate db at `DECISION_LEDGER_DB_PATH`
    41→defaulting to `/app/data/decision_ledger.db`)
    42→- **`decision_events`** — `(id, timestamp, decision_id, stage, token_id,
    43→  strategy, pnl, data_json)` — the main chronological chain.
    44→  Indexes: `(decision_id, timestamp ASC)` for chain reconstruction,
    45→  `(token_id, timestamp DESC)` for the token-level feed, `(stage)` for
    46→  per-stage aggregate queries.
    47→- **`decision_rejections`** — `(id, timestamp, decision_id, token_id,
    48→  strategy, predicted_edge, confidence, reason, market_mid)` — a fast
    49→  filtered rejection view. Each rejection is also written to
    50→  `decision_events` with `stage='RISK_REJECTED'` so the originating
    51→  `decision_id`'s chain has a complete end-to-end trail.
    52→- WAL-friendly `CREATE TABLE IF NOT EXISTS` + `CREATE INDEX IF NOT EXISTS`
    53→  idempotent init — safe to call on every boot.
    54→
    55→#### Public API
    56→- `decision_ledger.new_decision_id() -> str` — returns a fresh
    57→  `dec-{uuid4.hex}` (32 hex chars after prefix; globally unique, sortable
    58→  prefix for log grepping).
    59→- `decision_ledger.record(decision_id, stage, token_id=None,
    60→  strategy=None, pnl=0.0, **data)` — async write. `**data` is JSON-serialised
    61→  (with `default=str` for Decimals / enums / dataclasses) and stored in
    62→  `data_json`. Empty `decision_id` is skipped silently (legacy / manual
    63→  orders don't break the ledger).
    64→- `decision_ledger.record_rejection(token_id, strategy, predicted_edge,
    65→  confidence, reason, market_mid=None, decision_id="")` — async write.
    66→  Records BOTH a `RISK_REJECTED` chain event (if `decision_id` provided)
    67→  AND a row in the `decision_rejections` table.
    68→- `decision_ledger.get_chain(decision_id) -> list[dict]` — chronological
    69→  (oldest-first) stage chain. Each row includes both raw `data_json` and a
    70→  decoded `data` key for caller convenience.
    71→- `decision_ledger.get_chain_by_token(token_id, limit=50) -> list[dict]` —
    72→  most-recent-first stage events for a token.
    73→- `decision_ledger.get_rejections(limit=50) -> list[dict]` — most-recent-
    74→  first rejection feed.
    75→- `register_routes(app)` — appends two FastAPI routes:
    76→  - `GET /api/decision/{token_id}?limit=N` — recent decision events for a
    77→    token (404 if none recorded). Returns `{token_id, count, events[]}`.
    78→  - `GET /api/decisions/rejected?limit=N` — recent rejections. Returns
    79→    `{count, rejections[]}`.

   227→### Notes / known behaviour
   228→- The `_emit_ledger` fire-and-forget pattern means ledger writes happen
   229→  *after* `_ml_signal` returns. Callers that need to verify the chain
   230→  synchronously must `await asyncio.sleep(...)` (typically 100-150 ms is
   231→  enough for SQLite WAL writes to flush on a non-loaded system). Production
   232→  callers (the strategy scan loop) don't need to wait — the writes
   233→  eventually land.
   234→- The `record()` and `record_rejection()` methods both use
   235→  `asyncio.to_thread(_insert)` for SQLite I/O, so they don't block the
   236→  event loop. Combined with `_emit_ledger`'s `ensure_future`, the strategy
   237→  scan cadence is unaffected.
   238→- A missing / empty `decision_id` is silently skipped on writes (and
   239→  returns `[]` on `get_chain`). This preserves backward compatibility for
   240→  manual / legacy order paths (`/api/trade`, `position_manager.exit_order`,
   241→  etc.) that don't yet participate in the unified ledger.
   242→- The `decision_rejections` table duplicates the rejection info that's
   243→  also in `decision_events` (as a `RISK_REJECTED` stage row). This is
   244→  intentional — the rejections table is indexed for fast filtered listing
   245→  on the dashboard, while the chain row keeps the originating
   246→  `decision_id`'s audit trail complete.
   247→- The FILL stage records `pnl=0.0` for opening BUY orders (no P&L
   248→  realised until the position is closed). This mirrors the existing
   249→  `_execute_fill` P&L logic in `paper/simulator.py` (P&L is only computed
   250→  for SELL orders closing a long position).
   251→- Live-mode orders (`paper=False`) currently flow through `clob_client`
   252→  without a ledger ORDER stage record (only PREDICTION → SIGNAL →
   253→  RISK_APPROVED is recorded for live orders). Adding an ORDER stage for
   254→  live orders would require either extending `clob_client.create_order`'s
   255→  return shape or wrapping it in `strategies/base.py`; out of scope for
   256→  R11+R12 (the task spec only mentions paper `create_order`).

   273→## R10 — Fix ML predict endpoint + add one-click position close
   274→- **Date:** 2025-09-03
   275→- **Scope:** `mini-services/polymarket-bot/api/server.py` (additive only; no existing code removed)
   276→
   277→### Background / investigation
   278→- `core/market_discovery.py` exposes a singleton `market_discovery` whose
   279→  `catalog: dict[str, dict]` (token_id → market metadata) is the canonical
   280→  in-memory market index. The task explicitly requires reading market
   281→  metadata from `market_discovery.catalog` — the `store.market_info`
   282→  attribute referenced in earlier draft specs **does not exist** on
   283→  `core/data_store.DataStore` (verified by grep + runtime import).
   284→- `ml/model.py::MarketMLModel.predict(features, token_id)` returns
   285→  `(p_yes, confidence)`; `confidence = |p_yes − 0.5| × 2`.
   286→- `ml/features.py::extract_features(market, book)` expects a Gamma-style
   287→  market dict (`volume24hr`, `volume`, `liquidity|liquidityNum`,
   288→  `endDate|end_date_iso|endDateIso`). The catalog record uses normalized
   289→  snake_case keys (`volume_24h`, `total_volume`, `liquidity`, `end_date`),
   290→  so the predict endpoint bridges both shapes before feature extraction.
   291→- `core/data_store.Position` carries `yes_shares` (long YES) and
   292→  `no_shares` (long NO). Closing a long YES → SELL at best_bid; closing a
   293→  long NO → BUY at best_ask (symmetric synthetic-short cover).
   294→- Risk gate (`risk.manager.RiskManager.check_order`) is applied on every
   295→  order — close orders are not exempt (consistent with `/api/trade`).
   296→- `paper/simulator.PaperSimulator._can_fill` fills a SELL at price=best_bid
   297→  whenever `best_bid ≥ price` (true by construction), so a marketable
   298→  close order settles in the ~1s paper fill-loop.
   299→
   300→### Changes (all additive — no existing endpoints modified)
   301→
   302→#### 1. `GET /api/ai/predict/{token_id}` (tag: `ai`)
   303→- Reads metadata from `market_discovery.catalog[token_id]`; 404 if absent
   304→  (hint: retry after next catalog sync, or check `/api/markets/coverage`).
   305→- Fetches live `OrderBook` via `store.get_order_book`; 502 + poller hint
   306→  if absent.
   307→- Builds a feature-compatible market dict (snake_case → Gamma-style aliases)
   308→  and calls `ml.features.extract_features` + `ml_model.predict`.
   309→- Returns:
   310→  - `p_yes`, `confidence`, `market_mid`, `best_bid`, `best_ask`, `spread`
   311→  - `edge = p_yes − market_mid` and `edge_bps` (basis points)
   312→  - `recommended_action`: `BUY` / `SELL` / `HOLD`
   313→    - **BUY**: `edge ≥ +2 ct (200 bps)` AND `confidence ≥ 0.10`
   314→    - **SELL**: `edge ≤ −2 ct (−200 bps)` AND `confidence ≥ 0.10`
   315→    - **HOLD**: otherwise (insufficient edge OR insufficient model conviction)
   316→    - Edge-based (not absolute p_yes) so a model that sees a 50/50 coin
   317→      priced at 0.20 surfaces BUY rather than HOLD merely because
   318→      `|p_yes − 0.5|` is small.
   319→  - `action_reason`: human-readable string explaining the decision
   320→  - `thresholds`: the gates used (auditable)
   321→  - `model_status`: model_ready, version, brier, roc_auc, ece, n_updates
   322→  - `market`: compact catalog payload (token_id, event_id, question,
   323→    slug, outcome, category, end_date, status, volume_24h, total_volume,
   324→    liquidity, last_synced)
   325→  - `book_updated_at`, `timestamp`
   326→
   327→#### 2. `POST /api/positions/{token_id}/close` (tag: `trading`)
   328→- Optional JSON body (`PositionCloseRequest`):
   329→  - `max_size_shares: float | None` — cap for partial scale-outs
   330→  - `dry_run: bool` — preview without submitting
   331→- Looks up position under `store._lock` (snapshots values before release).
   332→- 404 if no open position (`yes_shares ≤ 0 AND no_shares ≤ 0`).
   333→- Determines side from position direction:
   334→  - Long YES → `SELL` at `best_bid` (marketable limit; any bid ≥ best_bid
   335→    matches immediately)
   336→  - Long NO → `BUY` at `best_ask` (symmetric synthetic-short cover)
   337→- 502 + poller hint if book missing or both sides empty; specific 502 if
   338→  the relevant side (bid for YES close, ask for NO close) is empty.
   339→- Computes `estimated_pnl` for YES-close using cost basis
   340→  (`(close_price − avg_entry_price) × size_shares`).
   341→- `dry_run=true` returns the preview without submitting (includes
   342→  `remaining_position` projection).
   343→- Applies `risk_manager.check_order` (same gate as `/api/trade`);
   344→  400 with reason on rejection.
   345→- Submits `OrderArgs(order_type="FOK")` through `paper_sim` (paper mode)
   346→  or `clob_client` (live mode); for live mode constructs and stores the
   347→  resulting `Order`.
   348→- Writes an immutable `audit_logger.log_event` row
   349→  (`category=trading`, `event_type=position_close`).
   350→- Emits a `store.log_event` user-visible event line.
   351→- Returns: `status`, `order_id`, `side`, `price`, `size_shares`,
   352→  `notional_usdc`, `estimated_pnl`, `best_bid`, `best_ask`,
   353→  `book_updated_at`, `paper_trade`, `remaining_position` (post-close
   354→  projection), `note`.
