   142→  the `**data` payload round-trips through `json.dumps` →
   143→  `json.loads`. For values like `0.62` the round-trip is exact in

   147→  guarantees strictly-increasing `time.time()` values, regardless
   148→  of host clock resolution. SQLite stores REAL with µs precision —

   177→### Background / investigation
   178→- The trading pipeline already existed as discrete stages — ML predict →
   179→  signal generation → risk gate → order submission → fill — but each stage
   180→  logged to a different store (`audit_trail.db`, `store_state.json`,
   181→  in-memory `event_log`). Tracing the lifecycle of a single decision
   182→  required correlating timestamps across three data sources, with no
   183→  canonical id linking them.
   184→- `core/audit_logger.py` already establishes the SQLite + `asyncio.to_thread`
   185→  pattern used here; the new ledger mirrors that convention so the two
   186→  databases coexist without schema contention.
   187→- `strategies/signal_trader._ml_signal` is **synchronous** (returns
   188→  `MarketSignal | None` directly). The decision-ledger writes are async, so
   189→  the strategy uses a fire-and-forget pattern (`asyncio.ensure_future` on the
   190→  running loop) — this is critical because awaiting each ledger write inline
   191→  would block the 15 s scan cadence on SQLite I/O.
   192→- The four rejection paths in `_ml_signal` are:
   193→  1. `confidence < self._min_confidence` → `low_confidence`
   194→  2. `spread >= 0.04` → `wide_spread`
   195→  3. `0.45 < p_yes < 0.55` → `neutral_zone`
   196→  4. `kelly_numerator <= MIN_KELLY_NUMERATOR` → `insufficient_kelly_edge`
   197→  Each path now calls `record_rejection()` with `decision_id`, `predicted_edge`,
   198→  `confidence`, `reason`, and `market_mid` before returning `None`.
   199→- `OrderArgs` (in `core/clob_client.py`) is the canonical order-shape passed
   200→  to `paper_sim.create_order` and `clob_client.create_order`. The
   201→  `decision_id` is passed as a separate kwarg through `submit_order` →
   202→  `create_order` (NOT added to `OrderArgs` itself, keeping that dataclass
   203→  untouched per "additive only — do NOT remove existing code").

   205→### R11 — New `core/decision_ledger.py`
   206→
   207→#### Schema (SQLite, separate db at `DECISION_LEDGER_DB_PATH`
   208→defaulting to `/app/data/decision_ledger.db`)
   209→- **`decision_events`** — `(id, timestamp, decision_id, stage, token_id,
   210→  strategy, pnl, data_json)` — the main chronological chain.
   211→  Indexes: `(decision_id, timestamp ASC)` for chain reconstruction,
   212→  `(token_id, timestamp DESC)` for the token-level feed, `(stage)` for
   213→  per-stage aggregate queries.
   214→- **`decision_rejections`** — `(id, timestamp, decision_id, token_id,
   215→  strategy, predicted_edge, confidence, reason, market_mid)` — a fast
   216→  filtered rejection view. Each rejection is also written to
   217→  `decision_events` with `stage='RISK_REJECTED'` so the originating
   218→  `decision_id`'s chain has a complete end-to-end trail.
   219→- WAL-friendly `CREATE TABLE IF NOT EXISTS` + `CREATE INDEX IF NOT EXISTS`
   220→  idempotent init — safe to call on every boot.
   221→
   222→#### Public API
   223→- `decision_ledger.new_decision_id() -> str` — returns a fresh
   224→  `dec-{uuid4.hex}` (32 hex chars after prefix; globally unique, sortable
   225→  prefix for log grepping).
   226→- `decision_ledger.record(decision_id, stage, token_id=None,
   227→  strategy=None, pnl=0.0, **data)` — async write. `**data` is JSON-serialised
   228→  (with `default=str` for Decimals / enums / dataclasses) and stored in
   229→  `data_json`. Empty `decision_id` is skipped silently (legacy / manual
   230→  orders don't break the ledger).
   231→- `decision_ledger.record_rejection(token_id, strategy, predicted_edge,
   232→  confidence, reason, market_mid=None, decision_id="")` — async write.
   233→  Records BOTH a `RISK_REJECTED` chain event (if `decision_id` provided)
   234→  AND a row in the `decision_rejections` table.
   235→- `decision_ledger.get_chain(decision_id) -> list[dict]` — chronological
   236→  (oldest-first) stage chain. Each row includes both raw `data_json` and a
   237→  decoded `data` key for caller convenience.
   238→- `decision_ledger.get_chain_by_token(token_id, limit=50) -> list[dict]` —
   239→  most-recent-first stage events for a token.
   240→- `decision_ledger.get_rejections(limit=50) -> list[dict]` — most-recent-
   241→  first rejection feed.
   242→- `register_routes(app)` — appends two FastAPI routes:
   243→  - `GET /api/decision/{token_id}?limit=N` — recent decision events for a
   244→    token (404 if none recorded). Returns `{token_id, count, events[]}`.
   245→  - `GET /api/decisions/rejected?limit=N` — recent rejections. Returns
   246→    `{count, rejections[]}`.
   247→
   248→#### Module-level constants
   249→Stage vocabulary (single source of truth across the pipeline):
   250→- `STAGE_PREDICTION = "PREDICTION"`
   251→- `STAGE_SIGNAL = "SIGNAL"`
   252→- `STAGE_RISK_APPROVED = "RISK_APPROVED"`
   253→- `STAGE_RISK_REJECTED = "RISK_REJECTED"`
   254→- `STAGE_ORDER = "ORDER"`
   255→- `STAGE_FILL = "FILL"`
   256→
   257→Rejection reason vocabulary:
   258→- `REASON_LOW_CONFIDENCE = "low_confidence"`

   260→- `REASON_NEUTRAL_ZONE = "neutral_zone"`
   261→- `REASON_INSUFFICIENT_KELLY_EDGE = "insufficient_kelly_edge"`

   394→### Notes / known behaviour
   395→- The `_emit_ledger` fire-and-forget pattern means ledger writes happen
   396→  *after* `_ml_signal` returns. Callers that need to verify the chain
   397→  synchronously must `await asyncio.sleep(...)` (typically 100-150 ms is
   398→  enough for SQLite WAL writes to flush on a non-loaded system). Production
   399→  callers (the strategy scan loop) don't need to wait — the writes
   400→  eventually land.
   401→- The `record()` and `record_rejection()` methods both use
   402→  `asyncio.to_thread(_insert)` for SQLite I/O, so they don't block the

   931→### Background / investigation
   932→- `paper/simulator.py` exposes two pure helpers that govern every paper
   933→  fill: `_can_fill(order, book) -> float | None` (marketable-crossing test)
   934→  and `_apply_slippage(order, raw_price, book) -> float` (three-component
   935→  slippage model: flat 1-tick crossing + size-impact from book depth +
   936→  deterministic queue position via SHA-256 of `order.order_id`).
   937→- The simulator module constructs a module-level singleton
   938→  `paper_sim = PaperSimulator()` at import time, which reads
   939→  `store.paper_balance`. The shared `core.data_store.store` singleton
   940→  calls `load_from_disk()` on its own import, reading
   941→  `STORE_STATE_PATH` (default `/app/data/store_state.json`). Several other
   942→  modules reachable from `paper.simulator` (`core.decision_ledger`,
   943→  `core.audit_logger`, `core.market_db`, `core.safety`, `ml.model`,
   944→  `ml.vector_store`) each read their own env-var-configured DB / file path
   945→  at module load. Without redirecting these, the test would (a) hit
   946→  `/app/data/...` which does not exist in the sandbox (harmless — early
   947→  return from `load_from_disk`) and (b) potentially clobber the repo's
   948→  real `data/store_state.json` if `paper_sim` were ever exercised through
   949→  a code path that calls `save_to_disk()`. The test never calls
   950→  `save_to_disk`, but redirecting every env var to `/tmp/paper_sim_tests/`
   951→  up-front makes the file hermetic and resilient to future changes.
   952→- `_can_fill` is a regular method (uses `self` but reads no instance
   953→  state); `_apply_slippage` is a `@staticmethod`. Both are synchronous.
   954→  Tests therefore don't need `pytest-asyncio` — they construct minimal
   955→  `Order` + `OrderBook` fixtures inline and call the helpers directly,
   956→  which keeps the test surface tiny and the failure mode obvious.
   957→- The slippage model is **deterministic by `order_id`**: the queue
   958→  component is `SHA-256(order.order_id)[0] & 0x01` (0 or 1 tick). To pin
   959→  the queue component in tests (4), (5), and (7), I pre-computed order_id
   960→  literals whose first SHA-256 byte has LSB 0 (e.g. `paper-test-buy-6`
   961→  → 0x28, `paper-test-sell-0` → 0x6c, `paper-test-overflow-4` → 0x76) so
   962→  the slippage reduces to a known quantity (crossing + size-impact only)
   963→  and the assertions can be exact (`== pytest.approx(raw_price ± 0.01)`).

  1786→## S15 — Closed positions journal + performance attribution
  1787→- **Date:** 2026-09-03
  1788→- **Scope:** NEW `core/closed_positions.py` (SQLite-backed closed-position
  1789→  journal) + NEW `core/attribution.py` (seven-dimension P&L attribution
  1790→  engine) + additive wiring into `api/server.py` (no existing endpoints
  1791→  modified; three new GET routes appended after the S13/S14 blocks).
  1792→
  1793→### Background / investigation
  1794→- The trading pipeline already records every executed fill in
  1795→  `paper/simulator._execute_fill` → `store.record_fill(Trade)`, but `Trade`
  1796→  rows only carry single-fill semantics (`side`, `price`, `size`, `pnl`,
  1797→  `strategy`, `paper`). They don't capture the **round-trip** shape a
  1798→  portfolio manager needs to answer attribution questions: entry price,
  1799→  exit price, holding period, originating strategy, model version, and the
  1800→  ML signal context (confidence / edge / p_yes / market_mid / liquidity
  1801→  at signal time) that drove the entry. A dedicated closed-positions
  1802→  journal was needed so attribution could slice P&L across strategy,
  1803→  confidence bucket, edge bucket, probability band, liquidity level,
  1804→  holding period, and trade direction.
  1805→- `core/decision_ledger.py` already establishes the SQLite + `asyncio.to_thread`
  1806→  + module-level singleton + `register_routes(app)` convention used here;
  1807→  both new modules mirror that convention so all four SQLite databases
  1808→  (`audit_trail.db`, `decision_ledger.db`, `closed_positions.db`,
  1809→  `market_intelligence.db`) coexist without schema contention.
  1810→- `core/portfolio.py::strategy_stats()` does per-strategy aggregation from
  1811→  in-memory `store.trades`, but: (a) it's strategy-only (no confidence /
  1812→  edge / probability dimensions), (b) it works off the in-memory trade list
  1813→  which is reset on every restart, and (c) it doesn't model round-trip
  1814→  holding period. S15 stores closed positions to SQLite so the journal
  1815→  survives restarts, and adds the missing dimensions.
  1816→- `paper/simulator._execute_fill` already computes `pnl =
  1817→  (fill_price - avg_entry_price) * fill_size` for SELL fills that close a
  1818→  long YES position; that's exactly the input a `record_closed_position`
  1819→  call would need (paired with the entry price + holding seconds from the
  1820→  originating BUY fill's `created_at`). Wiring that emit is left as an
  1821→  additive follow-up (see Open items) — S15 ships the journal + the
  1822→  attribution engine + the API surface; the producer-side wiring is
  1823→  intentionally decoupled so a backfill can populate historical positions
  1824→  from `store.trades` without touching the live fill path.
  1825→
  1826→### S15.1 — NEW `core/closed_positions.py`
  1827→
  1828→#### Schema (SQLite, separate db at `CLOSED_POSITIONS_DB_PATH`
  1829→defaulting to `/app/data/closed_positions.db`)
  1830→- **`closed_positions`** — `(id, timestamp, position_id, token_id,
  1831→  strategy, entry_price, exit_price, shares, pnl, holding_seconds,
  1832→  model_version, decision_id, direction, confidence, predicted_edge,
  1833→  p_yes, market_mid, liquidity, metadata_json)`.
  1834→  - `position_id TEXT NOT NULL UNIQUE` — idempotency key. Auto-generated
  1835→    as `pos-{uuid4.hex}` if the caller doesn't supply one; if supplied,
  1836→    `INSERT OR IGNORE` makes repeat calls a no-op.
  1837→  - The seven attribution dimensions (`decision_id`, `direction`,
  1838→    `confidence`, `predicted_edge`, `p_yes`, `market_mid`, `liquidity`)
  1839→    are first-class columns (not buried in `metadata_json`) so SQLite can
  1840→    `GROUP BY` them directly when the attribution engine needs to slice.
  1841→  - `metadata_json` is a catch-all for extras (slug, side, fees, etc.).
  1842→  - Indexes: `(token_id, timestamp DESC)` for the token-level feed,
  1843→    `(strategy, timestamp DESC)` for the strategy-filtered feed,
  1844→    `(timestamp DESC)` for the global recent-first feed.
  1845→- WAL-friendly `CREATE TABLE IF NOT EXISTS` + `CREATE INDEX IF NOT EXISTS`
  1846→  idempotent init — safe to call on every boot.
  1847→
  1848→#### Public API
  1849→- `closed_positions.record_closed_position(token_id, strategy,
  1850→  entry_price, exit_price, shares, pnl, holding_seconds,
  1851→  model_version="", **metadata) -> str` — async write. The required
  1852→  positional signature matches the task spec exactly; optional
  1853→  `**metadata` kwargs promote attribution dimensions (`decision_id`,
  1854→  `direction`, `confidence`, `predicted_edge`, `p_yes`, `market_mid`,
  1855→  `liquidity`) to dedicated columns and bundle the rest into
  1856→  `metadata_json`. Returns the `position_id` actually written (so
  1857→  idempotent callers can verify whether the row was new or pre-existing
  1858→  via a follow-up `get_closed_positions(position_id=...)` lookup).
  1859→- `closed_positions.get_closed_positions(limit=50, strategy=None)
  1860→  -> list[dict]` — async read. Most recent first. `strategy` filter is
  1861→  optional (None/empty = all). Each row carries the raw attribution
  1862→  columns plus a decoded `data` key (from `metadata_json`).
  1863→- `closed_positions.get_closed_stats() -> dict` — async aggregate roll-up
  1864→  returning `count`, `total_pnl`, `avg_pnl`, `median_pnl`, `win_rate`,
  1865→  `wins`, `losses`, `breakeven`, `avg_holding_seconds`, `gross_profit`,
  1866→  `gross_loss`, `profit_factor` (None when no losses), `best_trade`,
  1867→  `worst_trade`, `avg_entry_price`, `avg_exit_price`,
  1868→  `total_volume_shares`, `strategies_count`. Computed in a single SQL
  1869→  aggregate (median via a second `SELECT pnl ORDER BY pnl` query, since
  1870→  SQLite has no `MEDIAN()` builtin). Empty store returns a zeroed-out
  1871→  payload (no `null` fields, `profit_factor=None`) so the API never
  1872→  surfaces `null` on a fresh deployment.
  1873→- `register_routes(app)` — appends two FastAPI routes:
  1874→  - `GET /api/positions/closed?limit=N&strategy=X` — recent closed
  1875→    positions (filterable). Returns `{count, positions[]}`.
  1876→  - `GET /api/positions/closed/stats` — aggregate stats. Returns the dict
  1877→    documented on `get_closed_stats()`.
