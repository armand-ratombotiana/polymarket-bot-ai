The AI/ML engine has been transformed from a **paper-tiger demo** (Wave 1:
0 real training labels, AUC 0.97 from a randomly-permuted split = pure

of 0.57 is the honest answer to "can this model predict Polymarket
outcomes" — and an AUC of 0.57 is **statistically meaningful** above 0.50
(random) on the binary-outcome prediction task.

## 2. BEFORE State (Wave 1)

The ML stack shipped a **demo that looked impressive** but was **not
actually learning**.

### 2.1 Training data

- `ml/model.py::fit_initial` trained a real sklearn ensemble on **3 000
  synthetic coin-flip labels** (`training_data_kind:
  synthetic_coinflip_seed`). The labels were generated by `random.random()
  < 0.5` — pure noise.
- The model "learned" to predict `p_yes` from features that had **zero
  signal** because the labels were noise. The training process converged
  (sklearn's RF always converges on noise to ~50 % accuracy) but the
  resulting model was statistically equivalent to a coin flip.

### 2.2 Train/test split methodology

- `ml/model.py::train_test_split` used `sklearn.model_selection.train_test_split`
  with **default arguments** — random permutation of the feature matrix.
- This is the **canonical lookahead-bias trap** for time-series ML: the
  test set contains rows whose timestamps are *before* the training set's
  latest timestamp. The model is being evaluated on data it has already
  seen (because the rows are interleaved with the training rows in time,
  and the features for later rows leak information about earlier outcomes).
- The reported AUC was **0.97** — a tell-tale sign of lookahead bias.
  Real binary-outcome prediction tasks on Polymarket typically achieve
  AUC 0.55–0.65; anything above 0.70 should be treated with suspicion.

### 2.3 Drift detection

- `ml/model.py` had a `drift_status` field that was always set to
  `"HEALTHY"` (a stub). No actual drift detection was performed — the
  model could be trained on data from January and deployed in September
  with no check that the feature distribution had shifted.

### 2.4 Probability calibration

- The model's raw `predict_proba` output was used directly as the
  `p_yes` signal. No Platt scaling, no isotonic regression — the
  predicted probabilities were systematically biased (RF tends to push
  probabilities toward 0.5, LightGBM toward 0 / 1).

### 2.5 Explainability

- No feature-importance attribution, no SHAP, no per-prediction
  explanation. When a model predicted `p_yes = 0.78` for a market, the
  operator had no way to know *why* — which features drove the
  prediction.

### 2.6 A/B testing

- No A/B testing framework. The model was the model. There was no
  way to deploy a challenger model alongside the champion and compare
  their performance on the same set of markets.

### 2.7 Feature store

- No feature store. Features were computed on-the-fly inside
  `ml/features.py::extract_features(token_id)` at prediction time, then
  discarded. No historical feature vectors were persisted, no feature
  versioning, no feature lineage.

### 2.8 Model registry

- `data/model_registry.json` had **two simultaneously ACTIVE model
  versions** — the original assessment flagged this as a defect
  ("which model is actually serving predictions?"). Rollback was not
  supported (only "activate by version_id" which set the new version
  ACTIVE without unsetting the old).

### 2.9 Evidence (Wave 1)

- `download/polymarket-bot-ai/docs/CURRENT_STATE_ASSESSMENT.md`: "0 real
  ML labels", "AUC 0.97 — lookahead bias", "no drift detection", "no
  calibration", "two ACTIVE models".
- `ml/model.py` Wave 1 source: `n_online_updates = 0` (learning /
  retraining / reload were dead code paths).

## 3. AFTER State (Wave 16)

### 3.1 Real training labels (R5)

- `core/label_backfill.py` (R5) pages through resolved markets from the
  Polymarket Gamma API, builds a 38-dim feature vector per token from
  market metadata + a synthetic order book (since resolved markets no
  longer have a live CLOB book), and writes `(features, resolved_label)`
  rows into the SQLite `ml_feature_store` table.
- Retrain is triggered once ≥ 50 new labels accumulate.
- **2 090 labels** at the Wave 4 snapshot; **4 970 resolved labels** as
  of 2026-09-03 (16 170 total feature vectors in the store, of which
  30.7 % carry resolved labels).

### 3.2 Walk-forward time-ordered split (R7)

- `ml/validation.py::validate_cv` (R7, T3) replaces the random-permutation
  split with a **walk-forward time-ordered split**. The training set is
  everything before timestamp T, the validation set is everything in
  [T, T+Δ), and the walk-forward proceeds by sliding T forward in time.
- This is the **correct** methodology for time-series ML: the model is
  always evaluated on data whose timestamps are *after* the training
  set's latest timestamp.
- The resulting AUC is **0.57** — honest. This is a **lower** number
  than the 0.97 lookahead-biased AUC, but it is the **correct** answer.
  An AUC of 0.57 is statistically meaningful above 0.50 on binary-outcome
  prediction tasks.

### 3.3 Drift detection (R6 + W3)

- `ml/drift_detector.py` (R6 reset, W3 expanded) computes three drift
  metrics:
  - **PSI** (Population Stability Index) — the canonical drift metric
    for credit-scoring / ML monitoring. Threshold: PSI > 0.25 = "DRIFTED".
  - **KS** (Kolmogorov-Smirnov) — distributional shift on each feature.
  - **Brier score** — calibration drift (is the model's predicted
    probability distribution drifting over time?).
- The drift status is persisted to the model registry and surfaced via
  `GET /api/ml/drift`.
- Verified by `tests/test_drift_detector.py` (multiple test cases
  pinning each metric + the threshold logic).

### 3.4 Probability calibration (Wave 6 + Wave 16)

- `ml/calibration.py` ships two calibration methods:
  - **Platt scaling** — fits a logistic regression on the model's
    predicted probabilities vs the true labels.
  - **Isotonic regression** — non-parametric monotonic calibration.
- Calibration is applied as a post-processing step on the model's raw
  `predict_proba` output. The calibrated `p_yes` is what flows into
  the signal-trader's confidence computation.
- Verified by `tests/test_calibration.py` (multiple test cases pinning
  each method + the calibration monotonicity property).

### 3.5 SHAP explainability (W16-3)

- `ml/explainability.py` (W16-3) ships a SHAP-style feature-attribution
  module. For any `(features, model)` pair, it returns a per-feature
  attribution that explains **how much each feature contributed to the
  model's prediction**.
- Surfaced via `GET /api/ml/explain/{token_id}` — the operator can see,
  for any prediction, which features drove it.
- Verified by `tests/test_explainability.py` (multiple test cases
  pinning the attribution sum + the per-feature sign).

### 3.6 A/B testing framework (Wave 14)

- `ml/ab_testing.py` (Wave 14) ships an A/B testing framework that
  deploys a **champion** model and a **challenger** model in parallel.
  Every prediction goes to both models; the champion's prediction drives
  the trading decision, but both predictions are logged for offline
  comparison.
- A Bayesian significance test (Beta-Binomial) is used to decide when
  the challenger has accumulated enough evidence to be promoted to
  champion (or retired if it underperforms).
- Surfaced via `GET /api/ab/tests` and `GET /api/ab/test/{test_id}`.
- Verified by `tests/test_ab_testing.py` (multiple test cases pinning
  the test lifecycle: create → start → accumulate → decide → promote).

### 3.7 Feature store with versioning (W16-2)

- `ml/feature_store.py` (W16-2) ships a feature store with:
  - **Feature versioning** — every feature vector carries a
    `feature_version` field. Changing the feature schema (adding a
    new feature, modifying an existing one) increments the version,
    so old predictions are reproducible from the version they were
    computed against.
  - **Feature lineage** — every feature vector carries a `source`
    field (which API / data source produced it).
  - **Online + offline stores** — the online store is SQLite (low-latency
    reads for prediction), the offline store is the same SQLite with
    indexes for batch training.
- Surfaced via `GET /api/ml/features/{token_id}` and
  `GET /api/ml/feature-history/{token_id}`.
- Verified by `tests/test_feature_store.py` (multiple test cases
  pinning versioning + lineage + online/offline parity).

### 3.8 4-model ensemble + Level-2 meta-learner (R8 + Wave 6)

- `ml/model.py` (R8 refit + Wave 6 expansion) trains a 4-model ensemble:
  - **Random Forest** (sklearn) — robust baseline.
  - **Gradient Boosting** (sklearn) — captures non-linear interactions.
  - **SGD Classifier** (sklearn) — fast online updates.
  - **LightGBM** (lightgbm) — gradient boosting with high efficiency.
- A **Level-2 meta-learner** (`ml/ensemble_meta_learner.py`) stacks the
  four models' predictions as features for a final logistic-regression
  classifier. NaN/Inf dropping in the meta-learner refit (R8) ensures
  a single bad base-model prediction does not poison the stack.
- Verified by `tests/test_meta_learner.py` (multiple test cases
  pinning the stacking + NaN/Inf guard).

### 3.9 Model registry with rollback (T8)

- `ml/model_registry.py` (T8) + `ml/routes.py` (T8) ship a model
  registry that:
  - Supports versioned model registration.
  - Enforces a **single ACTIVE model** at any time (the Wave 1
    dual-ACTIVE defect is fixed).
  - Supports `POST /api/ml/rollback?version_id=X` to roll back to any
    of the 5 registered versions.
- Verified by `tests/test_model_registry.py` (multiple test cases
  pinning single-ACTIVE + rollback).

### 3.10 Shadow inference (T13)

- `ml/shadow_inference.py` (T13) ships a challenger-model shadow
  inference path: every prediction goes to the champion model
  (which drives the trading decision) AND to a logistic-regression
  baseline challenger (whose prediction is logged for offline
  comparison but does NOT drive trading).
- This is a simpler alternative to the A/B testing framework when
  the comparison is "is my fancy ensemble better than a logistic
  regression baseline?".
- Verified by `tests/test_shadow_inference.py` (multiple test cases
  pinning the shadow-vs-champion logging).

### 3.11 ML copilot (W16-8)

- `ml/copilot.py` (W16-8) ships a natural-language market analyst. The
  operator can ask "Why is the model predicting YES on this market?" and
  the copilot returns a human-readable explanation that combines:
  - The model's `p_yes` prediction.
  - The SHAP feature attributions.
  - The drift status (if drifted, the explanation notes which features
    have shifted).
  - The calibration status (if the model is over-confident, the
    explanation notes the calibration correction).
- Surfaced via `GET /api/ml/copilot/{token_id}`.
- Verified by `tests/test_ml_copilot.py` (multiple test cases pinning
  the explanation structure).

### 3.12 Training orchestrator (Wave 6)

- `ml/training_orchestrator.py` (Wave 6) ships a training pipeline that:
  - Pulls new labels from the feature store since the last training run.
  - Runs the leakage audit (T3, `validate_no_leakage`).
  - Trains the 4-model ensemble + meta-learner.
  - Calibrates (Platt + isotonic).
  - Computes drift metrics vs the previous model.
  - Registers the new model in the registry (with rollback capability).
  - Triggers shadow inference for comparison.
- Verified by `tests/test_training_orchestrator.py` (multiple test
  cases pinning the pipeline stages).

### 3.13 Leakage detection (T3)

- `ml/validation.py::validate_no_leakage` (T3) audits a feature matrix
  for leakage signals:
  - Exact-duplicate rows.
  - Near-duplicate rows with *conflicting* labels (the strongest
    leakage signal — the same features are showing up with both YES
    and NO outcomes).
  - Label-domain violations (non-binary labels).
  - Feature-shape mismatches.
- The leakage audit is opt-in via `run_leakage_check=True` on the
  `validate_cv` / `validate_oot` API call — production retrain paths do
  NOT automatically run it (R1 below).

### 3.14 Look-ahead detector in backtest (T4)

- `backtesting/engine.py::_LookAheadDetector` (T4) inspects every
  backtest for forward-leakage of future information into past decisions
  (LE_01..LE_03 aggregate checks).
- The detector runs only inside backtest replay, not on the live
  prediction path (R1 below).

## 6. What Remains

### R1 — Leakage audit not run on production feature store (partially fixed)
The `validate_no_leakage` audit is opt-in via `run_leakage_check=True` on
the `validate_cv` / `validate_oot` API call — production retrain paths
(`ml/model.py::fit_initial`, `ml/training_orchestrator.py`) do NOT
automatically run it. A retrain that ingests a leaked feature batch would
silently ship a leaky model. The look-ahead detector runs only inside
backtest replay, not on the live prediction path. The production feature
store has not been retrospectively audited against the new leakage
heuristic.

**Severity:** Medium. A leaked model would invalidate the ML-signal
strategy's edge in production, but the paper-mode 80 % win rate is
computed against real outcomes, so a leak would surface as a paper-mode
win-rate collapse before live activation.

### R2 — Synthetic order book for resolved markets
The `label_backfill.py` service reconstructs a synthetic order book from
Gamma's `outcomePrices + volume24hr + liquidity` metadata for resolved
markets. This is a *plausible* book, not a *historical* book — features
derived from the synthetic book (best bid/ask size, mid, spread,
momentum) are approximations of the live book at decision time.

### R3 — Small-N AUC
The walk-forward AUC of 0.57 is computed on the 4 970 resolved labels.
The confidence interval on the true AUC is wide. The right answer to
"is this model useful?" is "yes, but marginally, and only above random
(0.50)". The model should not be the sole driver of trading decisions
without the parallel `kelly_numerator` gate (which protects against
thin-edge signals).

### R4 — Online learning path is still dead code
`ml/model.py::n_online_updates = 0`. The model is retrained only by the
training orchestrator's batch retrain path (triggered when ≥ 50 new
labels accumulate). There is no true online learning (per-trade weight
updates).

### R5 — ML copilot explanation quality
The copilot's explanation is rule-based (template + SHAP attributions),
not LLM-generated. For a richer natural-language explanation, the
copilot should be wired to an LLM endpoint (the prompt is in the module
docstring; the LLM call is the next step).
